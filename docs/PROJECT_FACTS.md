# KhetAI — Project Facts & Frequently Asked Questions (FAQ)

This document provides definitive, factual answers regarding the architecture, algorithms, data sources, ML experimentation layer, and operational scope of KhetAI.

---

### 1. What problem does KhetAI solve?
KhetAI eliminates unscientific, intuition-based sugarcane irrigation by delivering localized, data-driven irrigation advice (Should I irrigate? When? How much water? How long to run the pump?) based on crop evapotranspiration, soil moisture depletion, and weather forecasts.

---

### 2. What is the input data?
- **Soil & Crop Metadata**: Soil type (field capacity, wilting point, AWC), root depth, planting date, crop variety, plot location.
- **Soil Telemetry**: Soil moisture % at 30cm depth, soil temperature, ambient humidity.
- **Weather Forecast**: 5-day temperature, humidity, wind speed, solar radiation, ET₀ (reference evapotranspiration), and precipitation.

---

### 3. Where does weather data come from?
Weather data comes live from the **Open-Meteo API** (using plot latitude and longitude). Weather responses are cached in PostgreSQL for 6 hours (`provenance: LIVE_API` or `CACHED_API`). If the Open-Meteo API is unreachable, historical seasonal temperature fallbacks are used (`provenance: FALLBACK`).

---

### 4. Are physical IoT sensors connected?
**No.** Physical IoT hardware devices are not connected to this repository. All sensor telemetry in KhetAI is generated by an automated, deterministic software telemetry simulator for development and software demonstration purposes.

---

### 5. How is sensor data generated?
Sensor data is generated by an internal telemetry simulator (`sensorSim.js`) that produces physics-consistent soil moisture depletion curves based on crop age, reference ET₀, soil field capacity, and logged irrigation events (`provenance: SIMULATED`).

---

### 6. What database is used?
**PostgreSQL** (hosted on Supabase or local PostgreSQL instance) accessed via **Prisma ORM**. PostgreSQL persists user profiles, plot profiles, simulated sensor telemetry, irrigation events, weather caches, and alert logs.

---

### 7. What is the primary irrigation algorithm?
The primary decision engine is the **FAO-56 Agronomic Irrigation Intelligence Engine** (`irrigationEngine.js`). It calculates:
- Crop Coefficient (\(K_c\)) based on growth stage (Germination, Tillering, Grand Growth, Maturity).
- Crop Evapotranspiration (\(ET_c = K_c \times ET_0\)).
- Management Allowed Depletion (MAD) threshold (typically 50% AWC).
- Net irrigation requirement (\(\text{mm}\)) and plot-level water volume (\(\text{m}^3\)) required to restore soil moisture to field capacity.

---

### 8. Is the current active irrigation engine ML?
**No.** The active, primary irrigation decision engine is **FAO-56 crop physics**. The ML layer is an experimental, secondary analytical model.

---

### 9. What ML model was trained?
A **Multiple Linear Regression (Ridge OLS, \(\lambda = 10^{-3}\))** model (`sugarcane-irrigation-v1`) was trained in Pure JavaScript on 13 standardized soil and microclimatic input features.

---

### 10. What dataset was used?
The external **Sugarcane Irrigation Dataset for SIDSS Framework** (Zenodo DOI: `10.5281/zenodo.19725692`), containing 1,500 rows and 18 attributes.

---

### 11. Was the dataset real or model-simulated?
**Model-simulated.** The dataset target variable `drip_liters_per_day` consists of computed irrigation requirement outputs generated by another CatBoost ML pipeline simulation described in the SIDSS research paper, not direct physical water flow meter readings.

---

### 12. What are the ML test metrics?
Evaluated on a held-out random test split of 225 rows (15% of the 1,500-row dataset):
- **\(\log_{10}\) Scale:** \(R^2 = 0.9421\), \(\text{MAE} = 0.1050\), \(\text{RMSE} = 0.1277\)
- **Original Liters/Day Scale:** \(R^2 = 0.8507\), \(\text{MAE} = 4.2286 \times 10^8 \text{ L/day}\), \(\text{RMSE} = 1.0103 \times 10^9 \text{ L/day}\)

*Note: \(R^2\) is reported strictly as a statistical coefficient of determination on this specific dataset test set, not as real-world field accuracy.*

---

### 13. Can the ML model override the agronomic engine?
**No.** The ML prediction is strictly a secondary analytical payload (`mlExperimentation`). The active recommendation (`activeRecommendation`) is hard-coded to `AGRONOMIC_BASELINE` and cannot be overridden by the ML output.

---

### 14. What happens when sensor data is stale?
If telemetry is older than 7 days, the data quality status becomes `INVALID` and the agronomic decision badge outputs **`INSUFFICIENT_DATA`**. KhetAI refuses to invent recommendations on stale sensor data.

---

### 15. What happens when the weather API fails?
The system falls back to PostgreSQL cached weather forecasts (`CACHED_API`). If no cached forecast exists, it falls back to seasonal historical climate averages (`FALLBACK`) and clearly flags the source in the UI.

---

### 16. What are the current limitations?
1. **Hardware Scope:** Telemetry is simulated (`provenance: SIMULATED`). No physical IoT hardware is connected.
2. **ML Generalizability:** The ML model was trained on a model-simulated research dataset; its predictions are marked `NOT_DIRECTLY_COMPARABLE` to KhetAI plot water volume.
3. **Operational Scope:** KhetAI is project demo-ready for software evaluations, not operationally validated for production commercial farming deployment.
